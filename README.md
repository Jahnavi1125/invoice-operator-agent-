## What it does

You give the agent a plain-English request, for example:

> "Find the latest invoice from Acme Supplies and enter it into the company finance system."

The agent works out the steps itself. It lists the invoice files, reads the PDFs, compares dates to find the latest one, opens the finance web app in a real browser, fills in the form, saves it, and checks the result. If the amount is above the company limit it stops and asks a human for approval before saving. After the run, a separate verifier re-reads the PDF and the web app and confirms the saved data is correct.

I deliberately kept the scope narrow (one business workflow, one mock company system) and made that one workflow genuinely autonomous instead of building many simulated ones.

## The loop

Goal -> Understand -> Plan -> Execute -> Observe -> Adapt -> Verify -> Complete

At each step the model receives the goal, the company rules, the tool list, and everything observed so far. It picks the next tool, my code runs it, and the result goes back to the model. This repeats until the model replies with a final answer or the step limit (25) is reached.

## Architecture

```
invoice-agent/
  mock_app/app.py        Mock company finance system (Flask): add-invoice form and invoice list
  data/invoices/*.pdf    Sample invoice PDFs (generated by make_invoices.py)
  data/company_context.md  Company rules, loaded into the agent's system prompt
  agent/loop.py          Agent loop: model call, tool dispatch, retries, audit log
  agent/tools.py         Tool implementations and tool schemas (Playwright browser, PDF/file readers, ask_human)
  agent/policy.py        Policy gate enforced in code (approval required above the limit)
  agent/memory.py        Run state (approval flag) and the JSONL audit log writer
  agent/verifier.py      Independent verifier: compares the PDF against the real saved record
  evals/run_evals.py     Runs several tasks end to end and reports pass/fail
  logs/                  run_log.jsonl (every step) and screenshots
```

**Tools available to the agent:** `list_files`, `read_pdf`, `read_text_file`, `open_page`, `read_page`, `fill_field`, `click`, `ask_human`.

### How the pieces fit

1. **Loop (`loop.py`)** calls Gemini with function calling. Automatic function calling is switched off so that my code executes every tool call. This lets me log each action and apply policy before anything happens.
2. **Tools (`tools.py`)** are generic. `read_page` returns the visible text plus the name, id and type of every form element and button, so the model discovers selectors from the page instead of having them hard-coded. Adding a new tool means adding one function and one schema entry. The loop does not change.
3. **Policy (`policy.py`)** runs inside the `click` tool. If the click is on a submit button and the amount in the form is above the limit, the click is blocked and the tool returns a message telling the agent to get human approval. The model cannot skip this by ignoring the rule in its prompt. Approval is only recorded when the human answers yes in `ask_human`.
4. **Memory (`memory.py`, `company_context.md`)** is deliberately simple: the company rules are loaded into the system prompt, the conversation history carries what the agent has found during the run, and a small state object tracks human approval.
5. **Verifier (`verifier.py`)** does not trust the agent. It reads the PDF itself, converts the expected values (for example date `2026-10-28` to `28/10/2026`, amount without commas), fetches the real invoice list page, and compares vendor, amount and due date. It also flags missing records and duplicates.
6. **Audit log:** every tool call, policy block, and human answer is appended to `logs/run_log.jsonl`. Screenshots are saved after page actions.

## Key design decisions

- **Own loop instead of an agent framework.** The loop is about 100 lines, so I can explain and change every part of it. It also made it easy to put logging and policy between the model's decision and the action.
- **Policy enforced in code, not just in the prompt.** The company rules are also in the prompt so the agent plans around them, but the approval rule is a hard block. A prompt rule alone depends on the model choosing to obey it.
- **Independent verification.** The agent's own claim of success is not accepted as proof. The verifier checks the saved record against the source document.
- **Generic browser tools.** The same tools and loop run any task on the mock app, and the tool interface would work on other web forms.
- **Retries and error handling around the model.** Temporary model errors (rate limits, 503) are retried with increasing waits. Permanent errors (daily quota used, model not found) stop immediately with a clear message instead of retrying pointlessly. If the browser is closed, the tools reopen it.
- **Strict evals.** An early version of my eval counted a run as a success when the agent had crashed and saved nothing. I changed it so a case only passes if the agent reached a final answer, saved or did not save as expected, and actually asked for approval when it should have.

## Setup and run (Windows, PowerShell)

Requirements: Python 3.10+ and a Gemini API key from Google AI Studio.

```
python -m venv venv
venv\Scripts\activate
pip install flask playwright pypdf reportlab python-dotenv google-genai
playwright install chromium
python make_invoices.py
```

Create a file named `.env` in the project root:

```
GEMINI_API_KEY=your_key_here
GEMINI_MODEL=<the model name you used>
```

`python list_models.py` prints the models your key can use.

Terminal 1, start the mock company system and leave it running:

```
venv\Scripts\activate
python mock_app/app.py
```

Terminal 2, run a task:

```
venv\Scripts\activate
python agent/loop.py "Find the latest invoice from Acme Supplies and enter it into the company finance system."
```

Then verify independently:

```
python agent/verifier.py ACM-1007
```

Useful extras:

- `http://127.0.0.1:5000/reset` clears the saved invoices (the app keeps data in memory).
- To test failure recovery, start the mock app with `$env:INJECT_FAILURE="1"; python mock_app/app.py`. The first Save then fails once with a temporary server error.
- Acme's latest invoice (INR 61,200) is above the INR 50,000 limit, so the agent will ask for approval in the terminal. Type `yes` or `no`.

## Models, libraries and services

- **Model:** Google Gemini via the `google-genai` SDK (function calling), model name set in `.env`. Free-tier API key.
- **Browser automation:** Playwright (Chromium).
- **Mock company system:** Flask.
- **PDF handling:** pypdf for reading, reportlab for generating the sample invoices.
- **Other:** python-dotenv.
- I used AI coding tools while building this. I can explain and modify every file in the repository.

## Assumptions

- The mock finance system stands in for a real internal system. No real company credentials, data or third-party systems are used. All invoices are made up.
- Invoice PDFs have a consistent text layout (vendor, invoice number, issue date, amount, due date).
- The company's rules fit in a short text file that can be placed in the prompt.
- A human is available at the terminal to answer approval questions.

## Known limitations

- **One workflow, one mock app.** The tools are generic, but I have only tested invoice entry and a few variations of it.
- **Policy is narrow.** The gate checks the amount field on submit clicks. Other rules (duplicates, date format) are only enforced by the mock app's validation and by the agent following the written rules.
- **Memory is minimal.** Nothing is learned across runs. Company rules come from a static file.
- **In-memory mock data.** Restarting the mock app clears saved invoices.
- **Verifier is tied to the mock app.** It parses this app's HTML table and these PDFs' text layout.
- **Model dependence.** Behaviour, step counts and speed vary with the model. The free tier has low daily limits and occasional overload errors, which cause slow runs and retries.
- **No sandboxing.** The agent can only read files under `data/`, but browser actions run on the real local machine.
- **Approval is a terminal prompt.** There is no web UI for approvals and no timeout if nobody answers.

## What I would build next

1. **Persistent company memory:** store procedures, past outcomes and corrections, and retrieve the relevant ones per task instead of one static rules file.
2. **A real policy engine:** rules written as data (limits, allowed domains, allowed actions per role), checked before every tool call, with approvals routed through Slack or email instead of a terminal.
3. **More tools and environments:** email and spreadsheets, a second web app, desktop automation, and an API-first path wherever one exists, with the browser as a fallback.
4. **Stronger verification:** verifiers generated per task type, plus screenshots and an evidence report attached to each completed task.
5. **A larger eval suite:** many tasks with injected failures (renamed fields, slow pages, duplicate records, layout changes), run on every change, tracking success rate, steps and cost.
6. **Reliability work:** model fallback, step and cost budgets, loop and stuck detection, resumable runs with saved state, and a queue for background execution.
7. **Security:** per-task credentials with least privilege, a sandboxed browser, and full audit trails.
